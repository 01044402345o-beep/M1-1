## 1. 목표와 범위

### 목표

`REPORT.md`에 글로 쓴 결론을 독자가 **직접 조건을 바꿔가며 확인·반증할 수 있게** 만든다. 특히 리포트의 가장 중요한 단서인 *"Drift가 이긴 것은 홀드아웃 30일이 상승 구간이었기 때문이며, 다른 구간이면 순위가 뒤집힌다"* 를 슬라이더 조작으로 재현할 수 있게 한다.

### 범위에 포함

- 기간 선택 → 선택 구간으로 지표 재계산
- 이동평균 구간 선택
- 변동성 윈도 선택 + 구간 요약 통계
- 홀드아웃 시작일 선택 → 베이스라인 3종 재평가
- URL 쿼리 파라미터로 상태 지정 (사람이 쓸 때는 위젯, 자동 캡처 시에는 주소)
- 스크린샷 4~6장 + 각 장면의 시나리오 설명 문서
- `README.md`에 실행 방법 추가

### 범위에서 제외

- 배포(Streamlit Community Cloud 등) — 계정 연동이 필요하고, 제출 형태로 스크린샷을 선택했으므로 불필요
- 실시간 데이터 갱신 — 기존 프로젝트와 동일하게 커밋된 CSV만 읽는다
- 신규 분석 기법 — 대시보드는 기존 분석을 **보여주는** 도구이며 새 분석을 추가하지 않는다
- 사용자 인증, 데이터 업로드, 종목 전환
- 매매 전략 시뮬레이션 — 선행 프로젝트의 비범위 항목을 그대로 승계한다

## 2. 접근 방식과 선택 근거

### 선택: Streamlit 앱이 `btc_analysis.py`를 직접 import

**근거**: 이 과제의 핵심 평가 항목은 "AI가 생성한 코드와 해석을 검증할 수 있는가"다. 대시보드가 표시하는 수치가 리포트의 수치와 **같은 검증된 함수**에서 나와야 그 검증이 성립한다. 기존 `btc_analysis.py`의 18개 함수는 전부 인자를 받는 순수 함수이고 36개 테스트가 덮고 있으므로, 대시보드는 계산을 재구현할 필요 없이 호출만 한다.

### 탈락시킨 대안

| 대안 | 탈락 이유 |
| --- | --- |
| 정적 HTML + Plotly (JS가 지표 재계산) | 기간을 바꿀 때 지표를 다시 계산하려면 이동평균·변동성 로직을 JavaScript로 재구현해야 한다. 검증된 모듈과 별개 구현이 둘로 갈려 이 과제가 가장 중시하는 지점에서 불리해진다. |
| 정적 HTML (Python이 조합별 결과를 사전 계산) | 기간×이동평균 조합을 전부 미리 구워야 해 선택지가 고정된다. 과제가 요구하는 "기간/조건을 바꿔보며 탐색"이 성립하지 않는다. |

## 3. 아키텍처

선행 프로젝트가 확립한 패턴 — **계산은 테스트된 순수 모듈에, 표현은 얇은 껍데기에** — 을 그대로 따른다.

```
btc_analysis.py       (기존, 수정 금지)  검증된 분석 함수 18개
      ↑
dashboard_core.py     (신규)            순수 함수. 파라미터 파싱·구간 슬라이싱·
                                        btc_analysis 호출 오케스트레이션. 테스트 대상
      ↑
dashboard.py          (신규)            Streamlit UI 껍데기. 위젯 배치와 렌더링만.
                                        계산 없음. 테스트 대상 아님
```

**`dashboard_core.py`를 분리하는 이유**: Streamlit 스크립트는 단위 테스트가 사실상 불가능하다(실행 자체가 런타임에 묶여 있다). 노트북 셀을 테스트할 수 없어서 `btc_analysis.py`를 분리했던 것과 **같은 이유, 같은 해법**이다. 파라미터 검증과 구간 슬라이싱은 경계 조건이 많아 반드시 테스트해야 하는 로직이므로 껍데기에 두면 안 된다.

### `dashboard_core.py` 공개 인터페이스

| 함수 | 역할 |
| --- | --- |
| `load_prepared(csv_path) -> pd.DataFrame` | `load_raw → drop_invalid_rows → reindex_daily → fill_prices → add_returns` 파이프라인 1회 실행 |
| `parse_params(raw, data_start, data_end) -> DashboardState` | URL 쿼리/위젯 입력을 검증·보정해 상태 객체로 반환 |
| `slice_period(df, start, end) -> pd.DataFrame` | 선택 구간 추출 |
| `recompute_indicators(df, ma_windows, vol_window) -> pd.DataFrame` | 슬라이스에 `add_moving_averages` + `add_volatility` 재적용 |
| `summarize_period(df) -> dict` | 구간 요약: 누적 수익률, MDD, 3σ 이상치 수(하락/상승), 연율 변동성 평균 |
| `evaluate_holdout_window(close, holdout_start, horizon) -> (preds, scores)` | 임의 시작일의 홀드아웃으로 `run_baselines` 재실행 |

`DashboardState`는 `dataclass`로 정의한다: `start`, `end`, `ma_windows`, `vol_window`, `holdout_start`, `horizon`.

> [2026-10-01] 위 표는 구현과 두 군데 다르다. (1) `load_prepared`는 표에 적힌 대로 `add_returns`까지 포함하지 않는다 — `add_returns`는 `recompute_indicators`로 옮겨졌다. (2) `summarize_period`는 단일 인자가 아니라 `summarize_period(df, vol_window)`로 `vol_window`를 받는다. 두 변경 모두 바로 아래 "지표 재계산 정책" 때문에 필요했다: `cum_return`을 포함한 지표가 선택 구간에 국한되려면 구간을 자르기 **전에** `load_prepared`가 그 지표를 계산해 둘 수 없고, 변동성 평균도 선택된 `vol_window`로 그때그때 다시 계산해야 하므로 `summarize_period`가 그 값을 인자로 받아야 한다. 즉 이 인터페이스 표와 재계산 정책 절이 서로 모순되며, 구현은 정책 절을 따랐다 — **정책 절이 우선한다.**

### 지표 재계산 정책 (중요)

기간을 바꾸면 **선택 구간의 데이터만으로 지표를 다시 계산한다.** 전 구간에서 계산한 뒤 잘라 보여주지 않는다.

근거: 30일 이동평균을 전 구간에서 계산한 뒤 2024년만 잘라 보면 그 값에는 2023년 데이터가 섞여 있다. 사용자가 "2024년의 30일 이동평균"을 보고 있다고 믿는 것과 다르다. 재계산이 사용자의 기대와 일치하는 동작이다.

**부작용과 그 처리**: 구간이 짧으면 윈도가 차지 않아 앞부분이 비고, 윈도보다 짧으면 지표가 전부 비어버린다. 이를 조용히 넘기지 않고 화면에 경고 문구로 표시한다 — 빈 그래프를 보여주며 아무 설명도 하지 않는 것이 가장 나쁜 동작이다.

### `evaluate_holdout_window`의 동작

`run_baselines`는 시리즈의 마지막 `horizon`일을 홀드아웃으로 자른다. 임의 시작일을 지원하려면 **종가 시리즈를 `holdout_start + horizon - 1`까지 자른 뒤** `run_baselines`를 호출하면 된다. 그러면 그 구간이 자동으로 "마지막 30일"이 된다.

**학습 구간을 최소 2일로 강제하는 이유**: `forecast_drift`의 기울기는 `(마지막값 − 첫값) / (길이 − 1)`이므로 학습 구간이 1일이면 0으로 나눈다. 선행 프로젝트의 최종 리뷰가 이를 발견했으나 당시 `horizon=30`이 고정이라 도달 불가능해 보류했다. **홀드아웃 시작일을 사용자가 움직이는 순간 이 경로가 도달 가능해진다.** `dashboard_core`가 입력 단계에서 막고, 그 경계를 테스트로 고정한다. `btc_analysis.py`는 수정하지 않는다 — 이미 리뷰를 통과했고, 호출자가 계약을 지키는 것이 옳은 해법이다.

이는 최종 리뷰 과정에서 2026-06 반사실 검증에 실제로 사용한 절차와 동일하며, 그 결과(Naive 10,578.53 < Drift 11,287.03 < 이동평균 11,526.55)가 리포트 7.4절에 기록돼 있다. **대시보드에서 홀드아웃을 2026-06-01로 맞추면 이 세 수치가 그대로 재현되어야 한다** — 구현 정확성을 검증할 수 있는 고정점이다.

## 4. 화면 구성

단일 페이지. 사이드바에 컨트롤, 본문에 4개 섹션.

### 사이드바 컨트롤

| 컨트롤 | 기본값 | 범위 |
| --- | --- | --- |
| 분석 기간 (시작/종료) | 전체 (2023-01-01 ~ 2026-09-29) | 데이터 범위 내 |
| 이동평균 구간 3개 | 7 / 30 / 90 | 2 ~ 200일 |
| 변동성 윈도 | 30 | 5 ~ 120일 |
| 홀드아웃 시작일 | 2026-08-31 (리포트 본 분석과 동일) | 학습 구간이 **최소 2일** 남는 범위 (아래 근거 참조) |
| 예측 구간 길이 | 30 | 7 ~ 90일 |

### 본문 섹션

1. **구간 요약** — 누적 수익률, MDD, 연율 변동성 평균, 3σ 이상치 수(하락/상승 분리). 숫자 카드 형태
2. **가격과 이동평균** — 선형/로그 축 토글
3. **일별 수익률과 롤링 변동성**
4. **베이스라인 예측 비교** — 실제 vs 3개 모델 + MAE/MAPE/방향 정확도 표, **MAE 최저 모델을 강조 표시**

4번 섹션에는 방향 정확도의 의미를 한 줄로 명시한다: 이 지표는 구간 전체에 대한 단 한 번의 방향 베팅이 맞았는지를 재며 모델 순위 판단에 쓰지 않는다. 리포트 7.3절·`evaluate_forecast` docstring과 동일한 내용이며, 셋이 어긋나면 안 된다.

### 시각화 방식

기존 `plots.py` 함수를 재사용하지 않고 Streamlit 안에서 matplotlib Figure를 직접 만들어 `st.pyplot`에 넘긴다.

근거: `plots.py`의 함수들은 **파일 경로를 받아 PNG로 저장**하는 것이 계약이다. 대시보드는 파일을 쓰지 않고 화면에 그려야 하므로 계약이 맞지 않는다. `plots.py`를 수정해 두 용도를 겸하게 만들면 이미 리뷰를 통과한 모듈이 복잡해진다. 색상 상수(`_RED`, `_BLUE` 등)와 폰트 설정 함수는 import해 재사용하여 리포트와 **동일한 시각 언어**를 유지한다.

## 6. 테스트 전략

### 테스트하는 것 (`tests/test_dashboard_core.py`)

- `parse_params`: 정상 입력, 결측 키, 잘못된 날짜 형식, 범위를 벗어난 날짜(양끝 보정), 역전된 시작/종료, 범위 밖 윈도 값
- `slice_period`: 경계 포함 여부, 빈 구간
- `recompute_indicators`: 슬라이스에서 재계산되는지(전 구간 값이 새지 않는지), 구간이 윈도보다 짧을 때 빈 결과
- `summarize_period`: 알려진 소형 시리즈에 대한 수계산 일치
- `evaluate_holdout_window`: 임의 시작일 슬라이싱이 올바른지, 학습 구간이 부족할 때 예외

### 테스트하지 않는 것

`dashboard.py` 자체. Streamlit 런타임에 묶여 있어 단위 테스트가 성립하지 않는다. 대신 **실제로 실행해 스크린샷을 찍고 사람이 눈으로 확인하는 것**이 이 계층의 검증이다. 선행 프로젝트에서 그래프를 눈으로 확인하는 단계가 실제로 색상 반전 결함을 잡아냈으므로, 이 방식은 형식적 절차가 아니다.

### 교차 검증 고정점

홀드아웃을 2026-06-01, 구간 30일로 설정했을 때 MAE가 Naive 10,578.53 / Drift 11,287.03 / 이동평균 11,526.55로 나와야 한다. 리포트 7.4절에 기록된 값이며, 대시보드가 독립 경로로 같은 값을 재현하면 구현이 옳다는 강한 증거가 된다.

## 7. 스크린샷 캡처 방법

Playwright + 시스템 Chrome(`channel="chrome"`)으로 자동 캡처한다. 사전 검증 완료: 실행 가능하며 한글과 음수 기호가 정상 렌더링됨.

**URL 쿼리 파라미터를 쓰는 이유**: Streamlit 위젯을 Playwright로 클릭하려면 내부 DOM 구조에 의존해야 하는데, 이는 버전이 바뀌면 깨지고 디버깅이 어렵다. 앱이 `st.query_params`를 읽게 만들면 캡처 스크립트는 **주소만 바꿔 이동**하면 되므로 그 취약점이 통째로 사라진다. 사람이 쓸 때는 평범하게 위젯으로 조작한다.

### 캡처할 장면 (5장)

| # | 설정 | 보여주는 것 |
| --- | --- | --- |
| 1 | 기본값 (전체 기간) | 대시보드 전체 모습 |
| 2 | 2023-01-01 ~ 2023-12-31 | 기간을 좁히면 지표가 재계산됨 |
| 3 | 이동평균 5/20/60으로 변경 | 조건 변경이 반영됨 |
| 4 | 홀드아웃 2026-08-31 (리포트 본 분석) | Drift 승리 재현 |
| 5 | 홀드아웃 2026-06-01 (하락 구간) | **순위 역전 — Naive 승리.** 리포트 7.4절 주장의 시각적 증명 |

4번과 5번을 나란히 두는 것이 이 스크린샷 세트의 핵심이다. 같은 모델, 같은 코드, 홀드아웃 구간만 바꿨을 때 결론이 뒤집히는 것을 보여준다.

| Python | 3.14.4 (기존 환경 그대로, venv 없음) |
| 추가 설치 | `streamlit` 1개 |
| 캡처 도구 | `playwright` (이미 설치됨) + 시스템 Chrome (확인됨) |

**리스크: `streamlit`이 Python 3.14에서 설치되지 않을 수 있다.** 3.14는 비교적 최신이라 일부 패키지의 휠이 아직 없을 수 있다.

**실패 시 행동**: 조용히 다른 프레임워크로 바꾸지 않는다. 설치 실패 사실과 오류를 보고하고 선택지를 다시 제시한다 — 접근 방식을 바꾸면 2절의 선택 근거(검증된 모듈 직접 재사용)가 무너질 수 있으므로, 그 판단은 사용자가 해야 한다.
